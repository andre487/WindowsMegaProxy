# v0.0.15

## English

- Added an early‑boot staged-update flow: when a service update is scheduled for reboot the installer extracts a signed "reboot" payload, verifies each file against the manifest, writes a reboot-files receipt and queues file replacements with MoveFileEx so Windows replaces binaries before services start.
- While a reboot replacement is queued the local client shows “Update in progress” (or “Restart Windows to finish the update. File replacement has already been scheduled.”) and disables Download/Install and mode‑change controls, preventing another download, mode change, repair or uninstall until after restart.
- The service requests extra startup time and verifies the reboot receipt and queued payload on startup; if verification fails the service blocks startup and records a recovery action so the verified installer will repair the installation after reboot instead of running incomplete binaries.
- Early‑boot updates require a system (all‑users) service installation and service mode; the installer accepts a BOOTUPDATE flag and stages reboot files to a temporary reboot folder and hands staging to the protected worker which enforces administrator ownership and ACLs.
- Scheduling a deferred service update for reboot sets the service start type to automatic so file replacement can occur before service startup, and the elevated worker writes a FilesQueued flag into the pending update record to prevent concurrent operations.
- Installer and service operations now refuse or error if queued reboot replacements are present (checks for Session Manager PendingFileRenameOperations and the reboot receipt), forcing users to restart Windows to finish the pending replacement before changing mode, repairing, cancelling or uninstalling.
- Staged reboot payloads are validated and deduplicated: paths are constrained (no escapes, links, update/uninstall paths or special names), payload counts and total size are limited, and every queued file must match its declared SHA‑256 and size or the staging/verification fails.
- The client UI and tray now surface the service’s installation/verification state (several UI texts, tooltips and the connection/status messages show “Update in progress” when FilesQueued or while an update worker is applying), and the application keeps waiting while the new service verifies its update.
- Smoke tests and UI checks were extended to simulate Session Manager file moves, exercise incomplete payload recovery and assert that queued replacements do not affect unrelated PendingFileRename entries; the native/diagnostics module dependency github.com/klauspost/compress was also bumped to v1.18.7.
- Installer behavior otherwise unchanged for normal (non‑reboot) updates and current‑user updates, which continue to use the existing installer workflow.

## Русский

- Добавлен механизм отсроченного обновления через раннюю замену файлов при загрузке: если обновление службы запланировано на перезагрузку, установщик распаковывает подписанный «reboot»‑пакет, проверяет каждый файл по манифесту, записывает квитанцию reboot‑files и ставит операции замены через MoveFileEx, чтобы Windows заменил бинарники до запуска служб.
- Пока замена, запланированная на перезагрузку, ожидает выполнения, локальный клиент показывает «Обновление в процессе» (или «Перезагрузите Windows для завершения обновления. Замена файлов уже запланирована.») и отключает кнопки загрузки/установки и изменение режима, предотвращая новую загрузку, смену режима, ремонт или удаление до перезагрузки.
- Служба при старте запрашивает дополнительное время и проверяет квитанцию и очередь файлов; при ошибке проверки сервис блокирует запуск и записывает информацию о восстановлении, чтобы после перезагрузки проверённый установщик восстановил установку вместо запуска неполного набора файлов.
- Ранние обновления требуют системной (для всех пользователей) установки сервиса и режима «service»: установщик принимает флаг BOOTUPDATE, помещает файлы в временную папку reboot и передаёт их защищённому воркеру, который устанавливает владельца и ACL, доступные только администраторам/системе.
- Планирование обновления службы с таймингом «reboot» переводит службу в старт=auto, чтобы замена произошла до старта сервиса, и подготовщик помечает запись PendingUpdate флагом FilesQueued, блокируя параллельные операции.
- Установщик и сервис теперь отказывают в изменениях/отмене/ремонте, если обнаружены очереди ранней замены (проверяется PendingFileRenameOperations и квитанция), требуя перезагрузки Windows для завершения замены перед изменениями.
- Сцена проверок и валидации: пути payload ограничены (никаких ../, внешних путей, специальных имен, ссылок или папок update/unins), файлы дедуплицируются, установлены пределы количества и суммарного размера, и каждый файл обязателен к проверке SHA‑256 и длины, иначе этап подготовки/верификации проваливается.
- Клиентский интерфейс и трей отображают состояние установки/верификации (несколько текстов, подсказок и сообщений соединения показывают «Update in progress» при FilesQueued или во время применения), а клиент остаётся в ожидании, пока новый сервис подтверждает своё обновление.
- Добавлены тесты и проверки UI для симуляции действий Session Manager, восстановления после неполной замены и изоляции очередей для разных установок; в native/diagnostics обновлена зависимость github.com/klauspost/compress до v1.18.7.
