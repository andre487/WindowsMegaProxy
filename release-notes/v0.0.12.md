# v0.0.12

## English

- Staged updates now write setup.exe to a .part file then atomically replace using a .previous backup, verify installer size/sha256 against a signed manifest before commit, and preserve a verified installer after a failed apply so administrators can retry manually; triggered when an install is interrupted or fails.
- Update discovery is separated from download: checks can report “update available” without downloading, and the UI shows a Download button to fetch the staged installer on demand; triggered when a check finds a newer release but download is not requested.
- Update checks and installer downloads can run through the configured proxy probe when AppUpdatePolicy is set to fetch through proxy, and checks are deferred with a UI notice if the engine/probe profile is not running; triggered when appUpdatesThroughProxy is enabled but no probe connection exists.
- App update downloads handle transient server errors with retries (up to 4 attempts on 5xx responses) and use an exponential backoff for repeated failed checks, increasing visibility of failure reason in diagnostics; triggered by HTTP 5xx responses or repeated download failures.
- New HTTP version control in the profile editor lets users choose Stable (HTTP/1.1), HTTP/2 or HTTP/2+HTTP/3, which are persisted as preferHttp2/preferHttp3 and cause the runtime to select the bundled "alpha" core when H2/H3 is required, with automatic fallback to HTTP/2 if HTTP/3 probes fail; triggered by user selection or probe results.
- Podkop (community list) rules gain a per-rule "update through proxy" option and podkop refresh now may use the engine probe transport or cache-only reads when requested; triggered when a rule has PodkopThroughProxy enabled or when only cached lists are available offline.
- Service broker now preserves unreadable global settings to settings-unreadable-<guid>.json, reports a Recovering state and configuration-repair message to the UI, and runs automatic recovery with exponential backoff and periodic health checks; triggered by corrupt settings or engine start/health failures.
- Installer repair no longer requires a previously installed helper: the installer copies repair helpers to {tmp}\repair and runs WindowsMegaProxy.Service.exe --prepare-repair to close prior instances, and the service will create a scheduled (unelevated) tray task to restore tray clients in logged-on sessions after boot-time updates; triggered during install over an existing root or after a boot update.
- UI and accessibility tweaks include an accessible Export format name, a consolidated HTTP version chooser in ProfileWindow, an Undo delete action for routing rules, updated connection/update status texts (e.g., "Recovering connection…" and revised update toast wording), and layout/scroll improvements; triggered by user interactions with profiles, rules, export, or when the service reports recovering/update states.
- CI and release automation now run a scripted release-package verification that downloads/verifies signed manifests and optionally validates a local signed candidate installer, and upload update-diagnostics artifacts for debugging upgrade failures; triggered by the release workflow and scripts/release_package.py --verify-upgrade.

## Русский

- Стадированные обновления теперь записывают setup.exe в временный .part файл и атомарно заменяют с .previous резервной копией, проверяют размер/sha256 установщика по подписанному манифесту перед фиксацией и сохраняют проверенный установщик при неудачной установке, чтобы можно было повторить вручную; срабатывает при прерывании или ошибке установки.
- Обнаружение обновления отделено от загрузки: проверка может показать «обновление доступно» без загрузки, а в интерфейсе появляется кнопка «Скачать» для выборочной загрузки подготовленного установщика; срабатывает, когда проверка находит новую версию, но загрузка не запрошена.
- Проверки обновлений и загрузка установщика могут выполняться через настроенный прокси‑пробник, если политика обновлений настроена на скачивание через прокси, а при отсутствии активного пробника проверки откладываются и показывают уведомление в UI; срабатывает, когда appUpdatesThroughProxy включён, но пробник не запущен.
- Загрузки обновлений повторяют попытки при временных ошибках сервера (до 4 попыток при 5xx) и используют экспоненциальную задержку для повторяющихся неудач, а причина ошибок теперь доступна в диагностике; срабатывает при HTTP 5xx или многократных сбоях загрузки.
- В профиле добавлен выбор версии HTTP: Stable (HTTP/1.1), HTTP/2 или HTTP/2+HTTP/3, сохраняемый как preferHttp2/preferHttp3; при запросе H2/H3 рантайм использует встроенное «alpha» ядро, а при неудаче H3 автоматически откатывается к HTTP/2; срабатывает по выбору пользователя или по результатам пробных проверок.
- Для Podkop (списков сообщества) добавлена опция «обновлять через прокси» на уровне правила, а обновление списков может выполняться через пробник или в режиме только кэша, если указано; срабатывает при включённом PodkopThroughProxy для правила или при доступности только кэша офлайн.
- Брокер сервиса сохраняет повреждённые глобальные настройки в settings-unreadable-<guid>.json, сообщает UI о состоянии Recovering с подсказкой по восстановлению и выполняет автоматическое восстановление с экспоненциальной задержкой и проверками состояния; срабатывает при повреждённых настройках или сбоях запуска/здоровья движка.
- Ремонт установщика больше не зависит от предыдущего helper: инсталлятор копирует вспомогательные файлы в {tmp}\repair и запускает WindowsMegaProxy.Service.exe --prepare-repair для закрытия старых экземпляров, а служба создаёт планировщик задач для восстановления непривилегированных tray‑клиентов в сессиях пользователей после обновления; срабатывает при установке поверх существующей корневой папки или после обновления при загрузке системы.
- В UI и доступности: доступное имя формата экспорта, единый селектор версии HTTP в окне профиля, кнопка Отменить удаление для правил маршрутизации, обновлённые тексты состояния подключения/обновления (например, «Recovering connection…») и улучшения компоновки/скроллинга; срабатывает при работе с профилями, правилами, экспортом или при сообщениях службы о восстановлении/обновлениях.
- CI и автоматизация релизов выполняют проверку релизного пакета: скачивают и проверяют подписанные манифесты, опционально валидируют локальный подписанный кандидат, и загружают артефакты diagnostics для отладки проблем обновления; срабатывает в workflow релиза и при вызове scripts/release_package.py --verify-upgrade.
